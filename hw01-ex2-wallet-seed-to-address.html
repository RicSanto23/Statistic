Summary

This page rebuilds the pipeline an Ethereum wallet uses to turn a mnemonic phrase into an address. BIP-39 turns 128 random bits into twelve words and stretches them into a 512-bit seed; BIP-32 derives a tree of keys from the seed, and the BIP-44 path m/44'/60'/0'/0/i picks the Ethereum ones; secp256k1 gives the public key; Keccak-256 shortens it to a 20-byte address; and EIP-55 hides a checksum in the letter case. For the public test phrase "test test … junk" the page produces 0xf39F…2266, the same first address a wallet such as MetaMask shows.

Each step is a different kind of operation: key generation, key derivation, public-key cryptography, hashing, checksum or encoding. Only the first step is random; everything after it is deterministic. The statistics confirm what each step promises: changing one bit of the original randomness changes about half of the bits of the seed, the private key and the address; random word lists pass the BIP-39 checksum about once in 16 tries; a one-character typo slips past EIP-55 only about 2–3 times in 10,000; and although the address is 160 bits long, it never carries more than the 128 bits of entropy in the twelve words.

What surprised me most: a wallet's whole security rests on that single random number. The 2048 PBKDF2 rounds, the hardened derivation and the hashes each protect against a specific attack, but none of them adds a single bit of entropy.

Check it in a real wallet

The homework suggests trying wallet software such as MetaMask, Rabby, Exodus or Rainbow. A safe way to do it:

  1. Use a separate browser profile (or a spare device) with no real funds in it.
  2. Install the wallet from its official website and choose "import an existing wallet" (the wording differs between wallets). Paste the public test phrase test test test test test test test test test test test junk.
  3. The first account should be 0xf39F…2266, the address this page computes for m/44'/60'/0'/0/0. Add a second and third account in the wallet and compare them with the paths …/0/1 and …/0/2 here.
  4. Try the same phrase in a second wallet. Wallets that follow BIP-44 for Ethereum show the same addresses; if one shows different ones, it uses a different path. That difference shows why the derivation path matters. Most browser wallets do not ask for a BIP-39 passphrase, so leave it empty when comparing.
  5. Remove the test wallet afterwards. The phrase is public, so anyone can move funds sent to these addresses.

The six building blocks

What each standard or primitive does, what goes in and what comes out, and why the pipeline needs it.

BIP-39

Mnemonic code, 2013
key generationencodingchecksumkey derivation

Takes 128–256 random bits, appends a SHA-256 checksum of 4–8 bits, and writes the result as 12–24 words from a fixed list of 2048 (11 bits per word). The words are then stretched into a 512-bit seed with PBKDF2-HMAC-SHA512: 2048 rounds, salt "mnemonic" plus an optional passphrase.

Random bits → words a person can write down → 512-bit seed.

BIP-32

Hierarchical deterministic wallets, 2012
key derivation

HMAC-SHA512 with the key "Bitcoin seed" turns the seed into a master private key and a chain code. Each child key is one more HMAC-SHA512 of its parent, so a single seed defines a whole tree of keys. "Hardened" children (marked ') mix in the private key, so a leaked child key cannot expose its parent.

One seed → a practically unlimited tree of private keys (about 4 billion children per key, up to 255 levels).

BIP-44

Multi-account paths, 2014
key derivation

A naming convention for the BIP-32 tree: m / purpose' / coin type' / account' / change / index. Ethereum uses m/44'/60'/0'/0/i, where 60 is Ethereum's registered coin type. Same phrase plus same path gives the same addresses in every compatible wallet.

Seed + path → the private key for account i.

secp256k1

Defined in SEC 2, 2000
public-key crypto

The elliptic curve y² = x³ + 7 over a 256-bit prime field. The public key is Q = kG: easy to compute, infeasible to reverse (the discrete logarithm problem from exercise 1). It is what lets the owner sign transactions (ECDSA) without revealing k.

256-bit private key → 512-bit public key (x, y).

Keccak-256

SHA-3 winner 2012, in Ethereum since 2015
hashing

A sponge-based hash with a 256-bit output. Ethereum hashes the 64-byte public key and keeps the last 20 bytes as the address. It uses the original Keccak padding, so its output differs from the standardized SHA3-256 (see section 5).

64-byte public key → 32-byte hash → 20-byte address.

EIP-55

Mixed-case checksum, 2016
checksumencoding

Hashes the lowercase hex address with Keccak-256 and writes each letter a–f in uppercase when the matching hex digit of that hash is 8 or more. This gives about 15 check bits without making the address longer, and software that ignores case still reads it.

Lowercase address → the same address with a checksum in its capital letters.

Same tool, different job

A step's kind comes from its purpose, not from the algorithm inside it. The pipeline reuses hash functions in three different roles:

SHA-256 as a checksumBIP-39 keeps only the first 4–8 bits of SHA-256 of the entropy, to catch a wrong word. Nobody relies on it for secrecy.
SHA-512 inside key derivationPBKDF2 and BIP-32 use HMAC-SHA512 to turn one secret into another. Here the hash works as a pseudorandom function keyed by a secret.
Keccak-256 twiceOnce as a hash (public key → address) and once as a checksum generator (EIP-55), applied to the address it produced.

How often does EIP-55 miss a typo?

Take a checksummed address, change one character to a different hex digit, and check whether the result still looks valid. It does only if the new address's checksum happens to match all its capital letters, which has probability 2−L for an address with L letters. Averaged over random addresses this is (13/16)⁴⁰ ≈ 0.0245%, close to the 0.0247% quoted in the EIP.

The pattern is the same one exercise 1 found. Generation, derivation and hashing all produce outputs that look perfectly random, and only generation is actually random. Checksums are measured by how often they miss an error, not by randomness. And secp256k1 is the one step that is deliberately structured, because that structure is what lets a public key verify a signature.

Historical context

The primitives are decades older than the wallet standards. Once Bitcoin created the need, BIP-32, BIP-39, BIP-44 and EIP-55 assembled them into a pipeline in just four years.

Filled dots: the dates in the homework. Open dots: context. The axis is compressed between 2002 and 2008.

Reading the order

The order goes from mathematics to standards to products to usability fixes. Public-key cryptography (1977), elliptic curves (1985) and the hash standards (2001) were decades of academic and standards work. Bitcoin (2009) then turned private keys into money, and managing them became a practical problem. The wallet standards answered it in quick succession, each building on the previous one: BIP-32 (2012) grew a tree of keys from one seed, BIP-39 (2013) made that seed writable as words, and BIP-44 (2014) fixed where in the tree each coin lives. Ethereum (2015) reused all three with its own coin type, 60, and its own hash, Keccak-256, adopted before SHA-3 was final. EIP-55 (2016) fixed a problem found in daily use: mistyped addresses.

Why RSA is on the list

RSA is not used anywhere in the wallet pipeline, but it is where public-key cryptography starts: the first practical system in which one key can be published while the other stays secret. Its security rests on factoring large numbers. Bitcoin and Ethereum chose elliptic curves instead because they give the same security with far smaller keys and signatures: a 256-bit secp256k1 key offers about the same security as a 3072-bit RSA key, and a signature takes 65 bytes instead of 384. That matters when every transaction ever made is stored by thousands of computers.

Keccak-256 is not SHA3-256. Both use the same permutation, the same rate (1088 bits) and the same 256-bit output. They differ only in padding: Keccak marks the end of the message with the byte 0x01, while the final SHA-3 standard adds two domain-separation bits and uses 0x06. Ethereum adopted Keccak while the standard was still being finalized and kept the original padding, so the two functions give completely different outputs for the same input.

Why not one algorithm for everything?

Because the wallet has several different problems to solve, and each primitive offers properties the others cannot.

The wallet needs…BIP-39BIP-32 / 44secp256k1Keccak-256EIP-55
a backup a person can write down
to slow down anyone guessing the phrase or passphrase
many unrelated keys from one backup
the same keys in every wallet
to prove ownership and sign without revealing the key
a short public identifier
to catch typos when copying

Key management (BIP-39, BIP-32, BIP-44). People need one backup they can write on paper; the system needs many keys. BIP-39 makes randomness writable and slow to brute-force, BIP-32 grows any number of keys from it, and BIP-44 makes every wallet grow the same tree.

Ownership (secp256k1). Public-key cryptography gives a pair where one half can be published and the other proves control through signatures. A plain hash cannot do this: to let others check that you know the input, you would have to reveal it, and then anyone could use it.

Identity (Keccak-256). A 64-byte public key is long to share. Hashing it gives a short 20-byte identifier, and the public key itself only becomes visible once the owner signs a transaction, because it can be recovered from the signature.

Error detection (EIP-55). Hex addresses were easy to mistype, and a mistake sends funds to an address nobody controls. A checksum catches accidents cheaply, without changing the address length or breaking old software. It is not a defence against attackers, who can compute it too.

Layering also keeps the system flexible: the same BIP-39 phrase works for Bitcoin by changing the coin type in the path, and EIP-55 was added in 2016 without changing a single key. A single algorithm would have to be at the same time random, human-readable, slow, fast, invertible and non-invertible, which is impossible.
