tl;dr

Summary

This page turns a private key into a public key with elliptic-curve scalar multiplication, the operation Ethereum uses on secp256k1. On the toy curve y² = x³ + 7 (mod 17), with base point G = (1, 5) and private key k = 6, the public key is Q = 6G = (5, 8). I compute it by repeated addition (5 group operations) and by double-and-add (3 operations), and an animation shows every step on the grid.

I repeated the experiment for many keys, base points and larger primes, running the same tests on Keccak-256 as a control group. On the classic hash-function tests (uniformity, bit balance, correlation, avalanche) the two cannot be told apart: over repeated runs both are rejected about 5% of the time, as chance predicts. Exact relations such as (a + b)G = aG + bG separate them perfectly: always true for the curve, practically never for the hash. Elliptic-curve keys look random but are full of structure, and their security comes from the size of the group, not from randomness.

What surprised me most: G = (1, 5) has only 9 multiples, so k = 6 and k = 15 give the same public key, and anyone can find the private key in at most 9 tries. On secp256k1 the same search would take up to about 10⁷⁷ tries.

Compute the toy public key

Define the curve and the base point, choose a private key, then add G to itself until you reach kG. The final point is the toy public key.

The points of y² = x³ + ax + b over the integers mod p, together with the point at infinity O, form a group. Adding two points P = (x₁, y₁) and R = (x₂, y₂) uses the slope λ of the line through them (or of the tangent, when the two points are the same):

P ≠ R:   λ = (y₂ − y₁) · (x₂ − x₁)⁻¹ mod p      P = R:   λ = (3x₁² + a) · (2y₁)⁻¹ mod p
x₃ = λ² − x₁ − x₂ mod p      y₃ = λ(x₁ − x₃) − y₁ mod p      and   P + (−P) = O

Here a = 0 and b = 7, exactly like secp256k1. The inverse (·)⁻¹ is computed with the extended Euclidean algorithm. Every result is also printed in the browser console (F12).

Repeated addition: G, 2G, 3G, …, kG

The faster way: double-and-add

Read k in binary from left to right: always double, and add G when the bit is 1. At most about 2·log₂ k operations instead of k − 1.

Where the rule comes from

Over the real numbers the same equation draws a smooth curve, and the addition rule is pure geometry: a straight line through P and R meets the curve in exactly one more point; mirroring it across the x-axis gives P + R. Doubling uses the tangent line. Modular arithmetic keeps the formulas and throws away the picture, which is why the points above look scattered.

Hidden structure

The tests above look at outputs one at a time. These three checks look for exact relations between outputs, on 1,000 random cases each. For Keccak the same equations are tried with addition mod p on (u, v).

Repeated experiments

One run gives one p-value, and p-values are random too. If the outputs really behave like uniform random values, repeating the experiment many times should give p-values spread evenly between 0 and 1, and about 5% of them below 0.05.

Which properties actually matter?

Scalar multiplication and hash functions are both easy to compute and hard to invert, but they promise different things. The "Your run" column fills in from the last experiment in section 3.

Same input, same digest, computed in linear time.
Hard to invert– The whole point
Recovering k from Q is the ECDLP. Best generic attacks need about √n steps: 2¹²⁸ for secp256k1, but a few steps on a toy curve.		 Essential
Preimage resistance: given a digest, finding any input is infeasible.
Uniform x and y– Expected, not the security argument
Multiples of a generator cover the subgroup evenly, so coordinates look uniform over the valid points. But only about half of all x values are on the curve, and y always comes in pairs y, p − y.		 Expected
A digest should be indistinguishable from uniform random bits.
Frequency of values, collisions– Opposite behaviour
k ↦ kG is a bijection for 1 ≤ k < n: no collisions ever. Repeats appear only because kG = (k + n)G.		 Hash-specific
A hash compresses, so collisions must exist; they must only be hard to find. Repeated values follow the birthday paradox.
Bit balance– Minor
Top bits are biased whenever p is not a power of two; for secp256k1, p is so close to 2²⁵⁶ that the bias is negligible. Not a security property.		 Hash-specific
Each output bit should be 1 with probability ½.
Input–output correlation– Misleading test
Pearson r ≈ 0, yet the map is full of exact algebraic relations: (a + b)G = aG + bG and x(kG) = x((n − k)G). ECDH and signatures depend on this structure.		 Hash-specific
A hash should behave like a random oracle: no usable relation between inputs and outputs at all.
Avalanche effect– Not required
Outputs of k and k + 1 look unrelated, but anyone holding kG can compute (k + 1)G = kG + G without knowing k.		 Hash design criterion
Flipping one input bit should flip each output bit with probability ½ (strict avalanche criterion).
Order of the base point– Specific to EC
G must have large prime order. In the toy, G = (1, 5) has order 9 and Q = 6G has order 3: an attacker only needs to try 9 keys.		 Not applicable
Hash functions have no group structure.

What the numbers say

Most of the tests in section 3 are the classic checks for hash functions: uniform output, balanced bits, no correlation, avalanche. On curves with prime order, scalar multiplication passes them just as well as Keccak-256 does, and repeating the experiment gives the same flat spread of p-values for both. On these tests the two functions cannot be told apart. The three relations in "Hidden structure" separate them perfectly: they hold 100% of the time for the curve and essentially never for the hash. Passing the statistical tests therefore proves nothing about one-wayness, and failing some of them would not break it either.

The properties that matter for elliptic-curve scalar multiplication as a one-way function are different: it must be deterministic and efficient (double-and-add), the group must be large, and the base point must have a large prime order so that the discrete logarithm problem has no shortcut. Security comes from the size of the group and the hardness of the ECDLP, not from statistical randomness. Even a curve whose outputs pass the tests is useless when the group is small: on the toy curve the key falls after trying at most 9 multiples of G.

The structure that would ruin a hash function is exactly what makes elliptic curves useful. Because a(bG) = b(aG), two people can agree on a shared secret (ECDH), and because addition is compatible with multiplication, Ethereum can verify ECDSA signatures with only the public key. A hash cannot do either; that is why Ethereum uses both: secp256k1 for keys and signatures, and Keccak-256 to turn the public key into an address (section 5).

The toy curve also shows that the group order matters: the 18-point group is not prime (18 = 2 · 3²), so points have orders 2, 3, 6, 9 or 18. Real curves like secp256k1 use a prime-order group so that no point lives in a small subgroup.
